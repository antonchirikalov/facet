# facet

Набор конвейеров на Claude Code, которые готовят проектные документы: требования из материалов
клиента, технический дизайн по требованиям, список вопросов клиенту, проверенный пропозал для
клиента, обзорную статью по теме с иллюстрациями. Каждый конвейер — это несколько подагентов Claude Code с разными ролями
(писатель, корректор, критик), которых по очереди вызывает скрипт Dynamic Workflow, и набор
детерминированных проверок на Python между ними.

## Что получается на выходе

| Конвейер | Что на входе | Что на выходе |
|---|---|---|
| Требования | папка с материалами клиента: письма, заметки встреч, выгрузки чатов, RFP, ответы клиента на вопросы | документ требований: роли, бизнес-контекст, функциональные и нефункциональные требования, ограничения, модель данных, интеграции, противоречия, пробелы, предположения, факты о среде |
| Вопросы клиенту (discovery) | документ требований | список вопросов к клиенту по пробелам и противоречиям, каждый со ссылкой на пункт требований |
| Технический дизайн | документ требований | дизайн решения с одной архитектурой, трассировкой решений к требованиям, рисками и предположениями; вопросы клиенту; схемы |
| Проверка пропозала | черновик пропозала, транскрипт звонка и документы клиента, папка рисунков | тот же пропозал после кругов независимой проверки; карта покрытия — каждая просьба клиента и место, где на неё ответ; список незакрытого |
| Статья | одна фраза: тема, читатель, объём, язык | статья с найденными в сети источниками, проверенными числами и схемами |

Что отличает эти документы от того, что модель пишет за один запрос:

- у каждой строки каждой таблицы указан источник: документ, место в нём и короткая цитата;
- противоречия между людьми клиента не сглаживаются, а выносятся в отдельную таблицу с обеими
  позициями и статусом;
- выводы аналитика отделены от слов клиента и помечены как предположения;
- в дизайне одна архитектура, без вариантов на выбор и без оценок сроков и денег, каждое
  решение отсылает к номеру требования;
- документ выходит на языке исходных материалов.

## Как это устроено

Каждый документ проходит несколько итераций правки. Одна итерация выглядит так:

1. Писатель пишет или правит документ.
2. Корректор исправляет то, что можно проверить механически: пересчитывает числа, открывает
   каждую ссылку на источник и правит неверные, сверяет формулировки с исходником.
3. Проверка на Python: обязательные разделы на месте, ни одного пустого, у каждой строки таблицы
   есть источник, идентификаторы не повторяются, нет расплывчатых слов вроде «по возможности» и
   «быстро», нет запрещённой разметки.
4. Критик (для статей — два: по существу и по стилю) оценивает то, что можно оценить только
   суждением: полнота, корректность, читаемость. Замечания нумеруются, писатель отвечает на
   каждое: исправлено или отклонено с причиной.

Итерации повторяются, пока критик не примет документ или пока качество не перестанет расти.
Всё, что осталось открытым, записывается в отдельный файл, а не пропускается.

Правила для каждого типа документа — структура разделов, колонки таблиц, что обязательно, что
запрещено, чек-лист критика — лежат в одном файле, профиле типа документа. Писатель, корректор
и критик читают один и тот же профиль, поэтому проверяют одно и то же.

Между этапами конвейер останавливается. Результат этапа лежит на диске обычными файлами: вы
читаете, правите что нужно и запускаете следующий этап. Если сессия прервалась, повторный запуск
подхватывает готовое и не делает работу второй раз.

## Как пользоваться

### Что нужно один раз

- Claude Code 2.1.271 или новее, `uv`, Node.js.
- Установить зависимости и проверить: `uv sync --extra dev`, затем `uv run pytest`.
- Для статей нужен поиск в сети: MCP-сервер `tavily-remote`. Для PDF на входе — MCP `pdf-reader`.
- Для схем нужен figgybanana: путь к нему в `PAPERBANANA_BIN` в `.claude/settings.local.json`,
  картинки идут через ss_gateway. Без него требования, вопросы и дизайн работают полностью.
- Ссылки на полные документы-образцы лежат в `exemplars.local.yaml` (см. `.example`); в
  репозитории только обезличенные скелеты.

Каждый запуск идёт в собственную папку внутри `docs-runs/`. Имя папки создаёт команда:

```bash
python -X utf8 tools/newrun.py --base docs-runs --label "Клиент А"
```

Она печатает путь вида `docs-runs/klient-a-20260921-101500`. Дальше он называется `<папка>`.
Запуск в папку, где уже лежит результат, скрипт отклоняет: либо новая папка, либо явное
`"continue": true` (продолжить прерванное), либо `"fresh": true` (сделать заново).

Все конвейеры запускаются из сессии Claude Code инструментом Workflow или одноимённым скиллом,
с аргументами в JSON. Параметр `now` — текущее время в ISO: скрипту не доступны часы, а по
времени он проверяет, не работает ли в этой папке другой запуск.

### Требования

1. Положите материалы клиента в `<папка>/inputs/`. Годятся `.md`, `.txt`, транскрипты, выгрузки
   чатов, письма; PDF читается через MCP.
2. Запустите скилл `/solution-design`:

   ```json
   {"runDir": "<папка>", "now": "2026-09-21T10:15:00+03:00",
    "order": "Требования к первой версии системы записи для сети клиник; противоречия не разрешать, выносить в открытые вопросы",
    "config": {"stages": ["requirements"]}}
   ```

3. Результат: `<папка>/requirements.md`. Рядом `UNRESOLVED.md` — что критик оставил открытым,
   `extracts/` — что извлечено из каждого документа, `rounds/req/` — записи и снимки каждой
   итерации. Правьте документ руками, если нужно: следующие этапы читают файл с диска.

### Вопросы клиенту

Тот же скилл на той же папке с `"config": {"stages": ["discovery"]}`. Нужен только
`requirements.md` — из конвейера или положенный руками. Результат: `discovery-questions.md`.

### Технический дизайн

1. Та же папка, `"config": {"stages": ["design"]}`. Две модели пишут независимых кандидатов,
   селектор выбирает лучшего, критик доводит его итерациями. Вопросы клиенту создаются заодно.
2. Результат: `design.md` с плейсхолдерами схем, `discovery-questions.md`,
   `design-candidates/` с обоими кандидатами, `rounds/design/`.
3. Схемы: скилл `/attn-figures`:

   ```json
   {"runDir": "<папка>", "articlePath": "<папка>/design.md", "figures": 5}
   ```

   Рисунки ложатся в `<папка>/figures/` шириной 2000 пикселей; исходные рендеры остаются в
   `figures-work/`, чтобы любую схему можно было перерисовать по той же команде. Критик
   рисунков — Kimi K3, пока есть квота: скрипт сначала проверяет ключ одной картинкой, а
   если лимит кончится посреди прогона, figgybanana сам переключается на Claude. Кто на самом
   деле принял каждый рисунок, скрипт выясняет по логу рендера (`tools/critic_used.py`) и пишет в
   лог прогона, а не верит отчёту иллюстратора.

   Рисунки трёх видов. `exact` — схема, где важно, что с чем соединено и на какой неделе;
   `illustration` — сцена или обложка; обе рисует figgybanana. `screen` — экран продукта, где
   важны числа и слова (сваи на стене, строки цены, баннер, дисклеймер). Его не генерируют: бриф
   кончается блоком Facts (тексты дословно из документа и арифметика, например
   `ceil((29 - 2 * 2) / 6) + 1 == 6`), `tools/figure_facts.py` проверяет его до рендера, а сам
   экран пишется HTML-макетом и снимается headless Chrome (`tools/render_html.py`). Генератор не
   держит счёт и текст: на Vista один такой экран занял тридцать кандидатов.

### Редакция для клиента

`requirements.md` и `design.md` — трассируемые версии: у каждой строки источник, метки,
заметки о наших материалах. Клиенту уходит отдельная редакция. Когда обе версии прочитаны
и приняты, та же папка с `"config": {"stages": ["client"]}` (только отдельно) даёт
`requirements.client.md`, `design.client.md` и `client-id-map.json` — карту старых номеров в
новые. Гейт проверяет, что в редакции нет следов кухни (`library/style/forbid/client-meta.txt`),
номера идут подряд, а каждая цитата клиента есть в извлечениях. В Confluence публикуется
клиентская редакция; документ с пометкой internal публикатор не отправит без `--allow-internal`.

### Проверка пропозала

Пропозал читает клиент, поэтому до того, как черновик увидит автор, его проверяет конвейер. Скилл
`/proposal-review` на копии черновика в новой папке:

```json
{"runDir": "<папка>", "document": "<папка>/prop.md",
 "sources": ["<материалы>/call-transcript.md", "<материалы>/client-scope.md"],
 "config": {"figuresDir": "<материалы>/figures", "maxRounds": 3}}
```

1. Агент карты покрытия выписывает из транскрипта и документов клиента каждую просьбу,
   опасение и вопрос: роль, таймкод, дословные слова и раздел пропозала, который отвечает, или
   «out of scope» с причиной. Результат — `<папка>/coverage-map.md`.
2. Гейт: нет «you/your» вне цитат, нет жирного, нет пустых ячеек (кроме колонок цены), каждое
   «section N» ведёт на раздел, рисунки подписаны «Figure N.» по порядку, цитаты дословны, у каждой
   строки карты есть место в документе (`tools/coverage.py`).
3. Независимый проверяющий читает пропозал вместе с источниками и открывает каждый рисунок:
   покрытие, противоречия между разделами и между текстом и рисунками, обещания, которых нет в
   плане, утверждения без опоры в источниках, голос по профилю. Вердикт `approved` или `revise`.
4. Редактор правит документ по нумерованным замечаниям, отвечая на каждое «fixed» или
   «declined» с причиной; числа, которые изменились на рисунках, он называет, а не перерисовывает.

Круги повторяются до принятия, застоя, полки или лимита. Каждый круг и каждый черновик лежат в
`rounds/proposal/`, незакрытое — в `UNRESOLVED.md`. Правила пропозала — в профиле
`.claude/skills/proposal-profile/`.

### Статья

1. Этап исследования, скилл `/explainer-article`:

   ```json
   {"runDir": "<папка>", "now": "2026-09-21T10:15:00+03:00",
    "brief": "Статья на русском для разработчика без опыта в ML: архитектура трансформера, 18–25 тысяч знаков, сквозной пример с числами; без истории и без кода",
    "config": {"stages": ["research"]}}
   ```

   На диске появятся `brief.md` (тема разбита на аспекты, по искателю на каждый), `sources/` с
   заметкой на каждый найденный источник и `material.md` — сводный разбор. Бриф можно поправить.

2. Этап письма: тот же вызов с `"stages": ["draft"]`. Результат — `article.md` с плейсхолдерами
   схем, записи итераций в `rounds/`, открытое в `UNRESOLVED.md`.
3. Схемы: `/attn-figures` с `articlePath` на `article.md`.

### Если скрипт отказался запускаться

- «уже лежит результат прошлого прогона» — новая папка, либо `continue`, либо `fresh`, см. выше.
- «похоже, идёт другой прогон» — в папке недавно работал другой запуск; если он точно завершён,
  добавьте `"ignoreBusy": true` в `config`.
- Сессия прервалась посреди этапа — запустите тот же этап с `"continue": true`.
- Разобраться, что произошло: `<папка>/tools.jsonl` — что показала каждая проверка;
  `logs/stop-audit.jsonl` — какие файлы записал каждый подагент; `<папка>/handoff.md` — что
  какому агенту передавалось.

## Устройство репозитория

- `.claude/workflows/` — четыре скрипта конвейеров: `solution-design.js` (требования, вопросы,
  дизайн), `proposal-review.js` (проверка пропозала), `explainer-article.js` (статья),
  `attn-figures.js` (схемы);
- `library/agents/` — 26 подагентов, у каждого контракт `agent.yaml` и промпт;
  `.claude/agents/` генерируется из них командой из `CLAUDE.md`;
- `.claude/skills/*-profile/` — профили типов документов; `exemplars/` — скелеты образцов;
- `tools/` — проверки и служебные команды на Python: гейт по содержимому, учёт итераций,
  перечисление файлов, применение правок писателя, уменьшение рисунков, публикация в Confluence,
  карта покрытия, факты точного экрана, рендер HTML-макета, проверка того, кто судил рисунок;
- `library/style/` — профиль голоса автора и списки запрещённых слов, редактируются как данные;
- `SPEC.md` — решения и план проекта; `docs/workflow-conventions.md` — правила для тех, кто
  правит скрипты; `docs/decisions/` — разборы с датами.

## Ограничения, о которых стоит знать

- Всё, что читают подагенты (промпты, профили, тексты задач), написано по-английски; документы
  при этом выходят на языке исходных материалов.
- Один запуск делает один этап. Это намеренно: между этапами человек читает результат.
- Схемы рисуются медленно: до часа на пять рисунков, с проверкой каждого второй моделью.
- Пропозал пока пишется по профилю вне конвейера: `proposal-review.js` проверяет и правит готовый
  черновик, но не пишет его с нуля. Сборка Word на корпоративном шаблоне тоже вне facet.
- Короткие документы за один запрос в чате и документы по профилю без полного конвейера
  описаны в `SPEC.md` как план и пока не сделаны.
