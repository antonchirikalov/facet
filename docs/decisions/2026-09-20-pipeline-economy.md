# Экономика и качество конвейера: замеры 19–20 сентября 2026

Три полных прогона требований на одном демо-входе (пять документов вымышленной сети ветклиник),
один прогон дизайна с иллюстрациями. Всё измерено по транскриптам подагентов, не по ощущениям.

## Где уходят токены (прогон требований v2, 27 агентов)

| статья | токенов | замечание |
|---|---|---|
| новый ввод в кэш | 4,0 млн | стартовый контекст агента ~25 тыс., из них ~16 тыс. — CLAUDE.md |
| чтение из кэша | 11,0 млн | 6,0 млн — один писатель: 26 правок Edit по одной за ход |
| вывод | 254 тыс. | 49 тыс. — корректор, переписавший 92 КБ ради нескольких правок |

Три вывода и три исправления:

1. **CLAUDE.md читал каждый подагент.** Платформа кладёт всю иерархию CLAUDE.md в контекст
   подагента блоком `instructions`. Роль агента — в промпте, документ — в профиле, входы и
   выходы — в задаче; CLAUDE.md добавлял только токены. Генератор ставит `omitClaudeMd: true`
   (Claude Code ≥ 2.1.271). Стартовый контекст носильщика: 25 → 11 → 4–8 тыс. токенов.
2. **Правка через Edit по одному вызову за ход дороже переписывания.** 72 правки в круге 3 v3
   прочитали 10,3 млн кэшированных токенов. Инструкция «пакетами» не работает: каждый вызов
   инструмента — ход. Решение — файл правок `{old, new}` и линейка `tools/apply_edits.py`.
3. **Корректор переписывал документ.** Правило «Edit, не Write» для корректоров оставлено:
   у них правок мало (9 и 3), цикл не разгоняется.

## Что не сработало и почему

- **Носильщики на haiku.** Экономия ~1% прогона. Платформа передаёт каждому подагенту последнее
  сообщение человека из чата как «запрос, который главнее задачи»; haiku выполнил его буквально
  (pytest, dry-run, отчёт в корень репозитория) и вернул выдуманную запись о трёх пройденных
  кругах, скрипт поверил и пропустил петлю. Sonnet тот же блок игнорирует. Носильщики на sonnet;
  промпты и хвост задачи называют переданный запрос контекстом; скрипт доверяет отчётам о кругах
  и гейта только в форме, которую печатает инструмент.
- **Слияние носильщиков.** Гейт и проверка диска стоят в разных точках круга с разными схемами;
  после сокращения контекста носильщик стоит ~8 тыс. токенов, переделка не окупается.

## Доля носильщиков (SPEC §12)

31 из 84 вызовов на статье (37 %), 12 из 27–32 на требованиях (38–44 %). Порог 50 % не достигнут;
по токенам носильщики после сокращения контекста — единицы процентов.

Каждое улучшение формы шло от конкретной ловушки в демо-документах, а не от общих соображений.

## Дизайн и иллюстрации

- Дизайн: победил кандидат на opus (99 КБ против 42 у sonnet), три круга, критик не принял,
  лучший круг первый. Рост 24 → 28 → 34 тыс. знаков прозы при 8 → 10 → 9 замечаниях: каждое
  замечание закрывалось абзацем. Критик три круга требовал рисунки, которых по конструкции ещё
  нет. Оба дефекта закрыты профилем `solution-design` (IGNORE плейсхолдеров; предпочтение
  замечаниям, закрываемым сокращением).
- Иллюстрации: пять рисунков за 3 ч 17 мин и 794 тыс. токенов; четыре приняты, компонентная
  схема после 24 итераций и двух перерисовок осталась с тремя точными дефектами (нет связи API →
  PostgreSQL, выдуманная стрелка бакет → PostgreSQL, однонаправленная стрелка SPA → API).
  Смотрящий агент их назвал верно. Квота Kimi K3 кончилась на второй фигуре, дальше судил
  sonnet — так же, как на статье. Время — это цена рисования с критиком внутри figgybanana:
  до 24 итераций на одну схему.

## Что дальше, по убыванию отдачи

1. Прогон дизайна через файл правок: ожидание — минус 6–8 млн чтений кэша на круг.
2. Ограничить итерации figgybanana на одну фигуру (сейчас до 24) и отдавать неудачную схему
   человеку после второй перерисовки: три часа на пять рисунков — дороже дизайна.
3. Режим v2 для требований: предыдущий документ как вход, новые ответы клиента как дельта,
   метки CHANGED/NEW — так живёт эталон на стадии RFP.
4. `tools/trace.py`: покрытие MUST-требований дизайном по идентификаторам — линейка вместо
   ручной проверки критика.
5. Извлечение длинных документов кусками, когда один источник больше окна одного агента.
